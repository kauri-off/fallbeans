# Состояние: с чего продолжать

Открытое состояние: что не проверено, сломано или начато, и с чего продолжать. Не история (она в git): без
хешей, дат и пометок «не закоммичено» — файл должен оставаться верным после коммита. Исправленное — удалять.

## Начать с

1. Перемерить производительность после визуального прохода: эта машина (`cargo xtask perf run`, затем
   `--upscaler fsr3`/`fsr1`) и huawei (`wl.sh`, `perf compare`). Смотреть прогрев (длительность, пики памяти,
   подвисания в первом раунде), hex-a-gone (тайлы ~13k → ~141k треугольников), режимы «Качество»/«Баланс»,
   thin LTO профиля `dist` против fat. Старые цифры (до прохода, i5-13600KF, RTX 5060 Ti, High, 1600×900, 30 с с
   ботами): jump-club 304 fps (1% low 156), portal-panic 285 (153), hex-a-gone 300 (152), door-dash 292 (155);
   DX12 с DXC: jump-club 136, portal-panic 102. huawei (окно 1280×720, Medium): лобби 38, jump-club 48,
   portal-panic 34, упор в рендер-поток.
2. Выпуск: `release.yml` целиком (nsis, AppImage, deb и сам релиз) после правок не проходил; `setup` на
   Windows-раннере (zip через bsdtar, `cargo install` cargo-about) не проверен.

## Решить автору

- «Авто» на RTX выбирает DLSS (пресет M, ~6 мс GPU против 1,6 у FSR 3.1 на RTX 5070 Laptop): пресет K или FSR 3.1
  первым.
- DLL NVIDIA и AMD рядом с AGPL-игрой: нужно ли исключение для связывания (§7).
- AGPL §13: сервер не показывает игрокам ссылку на свои исходники.
- Происхождение моделей в README («сделаны для этой игры») не подтверждено.

## План: падения ловятся до запуска

Этапы 1–3 (стенд, сценарии, monkey) сделаны. Дальше, по выбору автора:

4. `stress` с полной логикой клиента (+ «Прервать игру», выход/вход, уход хоста). Сценарии и monkey уже закрывают
   эти действия на стенде (без задержек и потерь сети); вероятно, хватит флага задержки/потерь у сервера стенда.
5. Линты `indexing_slicing`, `unwrap_used`, `expect_used`, `panic` в `crates/` по модулям.
6. Property-тесты ядра (proptest только в dev-зависимостях).
7. `cargo xtask smoke` на программном Vulkan (lavapipe) — локально: noop не проверяет драйверы.

## Не проверено

- Windows: `check` (детерминизм между ОС, тесты клиента с Bevy как DLL), стенд клиента, `setup` (`tar` для zip,
  git-sparse, путь LLVM), `doctor` (vswhere, rc.exe, makensis), DX12 с апскейлерами.
- `setup --dist` (cargo install трёх инструментов, musl), `play`/`play --dist` вживую, `dist` с копиями из
  `target/sdk`, `fuzz-ui` с `dylib_env`, путь повтора `scenarios::` в `check`.
- Апскейлеры на AMD и Intel (FSR 3.1 под Linux там не запускался), DLSS во Flatpak (видит ли песочница
  `libnvidia-ngx.so`).
- Слой валидации: на первом кадре DLSS два образа NGX в `UNDEFINED`; раз за прогон FSR 3.1 был залп
  `vkDestroyImageView` образов, занятых его командным буфером (не повторился).
- Самый долгий кадр входа в раунд на слабом клиенте: дольше 3 с — сервер отключит игрока.
- Стресс с ботами без `--release` (ядро в dev теперь с opt-level 3).
- Отчёт о падении на Windows: имена берутся из PDB, которого в установщике нет, — вероятно, без имён.

## Известные проблемы

- `DeviceLost`: восстановления нет (системы рендера паникуют раньше обработчика Bevy), клиент выходит и при
  следующем запуске объясняет. Причина сброса на RTX 5060 Ti (Windows, драйвер 617.14, Vulkan, DLSS 4.5, раунд
  tail-tag) не найдена.
- Шлейфы временных апскейлеров за частицами, дымкой, порталами и мотами: нет реактивной маски (следующий шаг —
  `ffxDispatchDescUpscaleGenerateReactiveMask`).
- Иконка окна не задана: в Windows на панели задач её нет.
- Автовыбор API (Vulkan, затем DX12) без маркера неудачного запуска; `WGPU_BACKEND` не действует.
- Тесты на грани таймаута под нагрузкой `check`: `scenarios::round_drum_roll` (лимит 15 с, отдельно ~15,7 с),
  `scenarios::the_owner_leaves_the_lobby` (паника `clock::steer`, после правки не повторялась — гонять ещё).
- Стресс: первый прогон после сборки иногда ловит замирание на 0,1–0,6 с. В начале раунда клиент несколько тиков
  предсказывает по старой арене — иногда одна «необъяснённая» расходимость. Откаты при толкании бобов
  `game::pace_pushes` откладывает до 8 тиков: в portal-panic у чекпоинта это «шквал откатов».
- «Хвостики»: передачу хвоста клиент узнаёт через RTT (5–16 расходимостей в минуту у stress при пороге 30);
  захват (`hold`) не предсказан. Тест «захват неуязвимого» (`core/fb_arena/tests/tail_tag.rs`) опирается на
  геометрию захвата.
- Replay теряет операцию над пешкой, вошедшей между теми же тиками, и не совпадает после пропуска тиков сервером
  (`MAX_CATCHUP` в `rooms/room.rs` сдвигает `arena.tick`, в записи следа нет).
- `DevCmd::Start` со списком игр не смотрит на `rounds`.
- Допуски `baseline.json` у карт на выживание широкие (первое выбывание ±5–9 с). Боты на «Скрытом мосту» не видят
  настоящих панелей и считают мост провалом. Лобби и подиум не проходят аудитов карт (`run_audits` — только `GAMES`).
- Пороги в логах подобраны на глаз (`watch.rs`: поправка от 0,5 м; `stats.rs`: кадр от 250 мс, потери от 5%, RTT
  от 250 мс; сервер: разрыв ввода от 0,2 с) — подправить по реальным логам.
- Сеть: надёжное сообщение, отвергнутое вендорным `lightyear_transport` (больше 64 КиБ или частичное старше 30 с),
  навсегда останавливает канал. Запись адреса в lightyear_udp живёт до следующего пакета; состояние netcode
  незавершённых подключений не чистится.
- Плотная сетка коллайдеров (`world.rs`) занимает память по габаритам всех статических коллайдеров.
- VPS (1 vCPU): от 24 игроков подвисания кадра 40–130 мс при недогруженном процессоре, причина не найдена; после
  переноса сетки навигации в поток и пулов по одному потоку не перемерено. `--max-tick-us` 1000 подобран под
  локальную машину (на VPS p99 тика 300–600 мкс).
